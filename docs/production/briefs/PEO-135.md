# PEO-135 · Content format: .peo parser in core and tools, one-time TOML converter (D-057)

## Goal

One .peo parser, written twice (core C++ and tools/content Python), reads any file in the D-057 format into the same tree of records and typed values, with errors naming file, line and column; a shared set of conformance cases proves the two agree. Nothing in content/ changes yet: converting content, resolving the parent chain from header paths and switching the loaders over are PEO-136; parsing queries and effects is PEO-132.

## Context

- docs/domains/items.md (this item's domain page); docs/production/decisions.md D-057 (the format) and D-055, D-056 (paths, calls, layout)
- docs/design/content-format.md: 'The rules in one screen', 'Strings and text' and 'Grammar (for the parsers, PEO-135)' are the spec. Sections 1 to 9 are examples of what the parsers must accept; use them as conformance cases

- docs/bottlenecks.md 'What counts': parsing runs once at startup. Today's TOML loads in ~30 ms release (PEO-008); the .peo parser should be in the same range for the same content, measured once in PEO-136

## Units

- core: peo/core/peo_format.hpp + src/core/src/peo_format.cpp, one concept: a .peo file parsed into records. Value kinds: Integer (a plain integer), Quantity (an integer in the base unit, plus its dimension: length, area, mass, volume, time, temperature, density, percent), Range (two Quantity or Integer of one dimension), Boolean (yes/no), String (its text after escapes and indent trimming, plus formatted: whether it was triple-quoted), Path (a bare dotted name), Expr (the raw text of a query, call or $role, balanced, for PEO-132), List, Block (fields in file order; a dotted lhs builds nested blocks, and setting the same key twice in one block is an error). `struct PeoRecord { std::string path; bool abstract; PeoValue value; std::uint32_t line; }` where value is a Block or, for the one-line form, any value. `struct PeoParse { std::vector<PeoRecord> records; std::vector<std::string> errors; };` `[[nodiscard]] PeoParse parse_peo(const ContentSource&);` Errors read `<path>:<line>:<col>: <message>` and parsing resumes at the next top-level record. Unit table and rounding as the Grammar section says; ft, in, yd and mi are an error saying lengths are metric. Allocation is fine (load time only); no I/O, no globals, deterministic
- test: tests/core/test_peo_format.cpp, TEST_SUITE("peo_format"), unit tier, in-memory sources: each value kind; a dotted lhs nesting; units converting with rounding (1.5 cm = 15 mm, 10 lb = 4536 g, 1 gal = 3785 ml, 2 h = 7200 s, 212 F = 100 C) and a range with one unit; `6 ft` rejected naming metric; verbatim string keeping `<b>` and a backslash as typed; triple string with \n, \" and trimmed indentation; an unknown escape rejected; a missing comma after a field, an unclosed brace, a duplicate key and a stray token each give one error with the right line and column, and the record after it still parses; expr capture of `self.carried.**{ material ~ item.material.wood.**, dims.l >= 150 mm, }` and of `$tool.durability.reduce(1)` inside a list
- tool: tools/content/peo.py, the Python parser to the same spec (stdlib only), returning the same tree as plain dataclasses, with the same error text
- tool: tests/peo_dump/peo_dump.cpp builds peo_peo_dump (headless, linked to peo::core, built with everything else): `peo_peo_dump <file.peo>...` prints canonical lines `<record path>\t<field path>\t<kind>\t<value>` (quantities as base integer plus dimension, strings escaped as golden.py does, formatted strings marked, lists by index) and the errors, exit 1 on any error. tools/content/peo.py has the same printer
- test: tests/content/peo/ holds conformance cases: cases built from the whole-file examples of docs/design/content-format.md sections 1 to 9 and the Grammar rules plus error cases, each with its expected canonical lines or errors in a .expect file beside it. tools/content/peo_conformance.py runs the Python parser over every case and diffs against .expect, and with `--engine <peo_peo_dump>` does the same for the C++ parser; test.py main() calls the Python half; tests/CMakeLists.txt adds ctest peo_conformance for the engine half (Python3 guard and skip message as content_golden)
- docs: docs/architecture.md 'Current code' gains peo_format.hpp; docs/wiki/api-reference.md and docs/wiki/build-and-test.md gain the header, peo_peo_dump and peo_conformance; docs/domains/items.md lists PEO-135 to PEO-137 in Queue

## Acceptance

- `python3 tools/verify.py` passes, with the peo_format suite in the unit tier and ctest peo_conformance green
- Every conformance case gives identical canonical lines from both parsers, and every error case gives the same error text from both
- Every example block in docs/design/content-format.md sections 1 to 9 that is a whole file (starts with a record header) parses with zero errors in both parsers
- src/core opens no file and includes no stream header; toml++ and content.cpp are unchanged
- content/ is unchanged and the game plays as before
