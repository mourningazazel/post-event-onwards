# PEO-032 · CI concurrency cancels per-commit runs on main, so breakage goes unseen

## Goal

A push to main always gets a CI result, so main cannot go red unobserved.

## Context

- .github/workflows/ci.yml
- docs/roles.md (the Builder fast-forwards to main)

## Units

- ci: the workflow sets concurrency with cancel-in-progress: true keyed on github.ref. The Builder pushes a unit at a time to main, so each push cancels the previous run: on 2026-09-29 runs 40 through 48 were all cancelled and the first result anyone saw was the last one, red. Keep cancel-in-progress for pull_request and for claude/** branches, where superseding is what you want, but never cancel a run on main.
- ci: confirm the fix by pushing two commits to a scratch branch configured like main and checking both runs complete.

## Acceptance

- two pushes in quick succession to main both produce a completed CI result, neither cancelled
- pull request and claude/** runs still cancel their predecessors

## Out of scope

- branch protection rules, which are a repository setting rather than a file in the repo
