# PEO-080 · Executor in core; thread the field and the Dead

## Goal

Core runs its heavy passes on an executor its caller hands it (D-035, ADR-0014): the field's tiles, the direction bytes, the scent-beside-Dead halves of speculate and, for big batches, the Dead's intents split across pieces, and every run is bit-identical to the serial one

## Context

- docs/adr/0014-threads-and-gpu-compute-in-core.md: core creates no thread; the executor is a parallel-for over N pieces; the five determinism rules (integers; combine by max, min or integer sum; per-unit slots read in index order; counter-based hashes; read one buffer, write another)
- docs/research/parallel-and-gpu.md section 4 (what splits, in order of value) and the measured scaling: 4 threads 3.0-3.7x on the field's tiles, 2 threads 1.75-2.0x; the Dead's intents only pay from a few hundred thousand units per batch (2 threads were slower than 1 at 50,000)
- src/core/src/world.cpp World::speculate(): out.scent.update() and the Dead's seconds up to the boundary are independent (the Dead read scent_, the update writes out.scent), so they are two pieces with no algorithm change
- src/core/src/scent_wave.cpp round(): pull_tile per active tile reads buffer A and writes buffer B, so tiles are independent within a round; touched() and the stale_ list are shared state and must be filled after the pieces, in tile order. update()'s direction-byte refresh writes a one-cell ring into neighbouring tiles, so two pieces could write the same cell: split it so no two pieces ever write one cell (for example each piece rewrites only its own tile's cells, for every tile that is stale or next to a stale one)
- src/app/main.cpp: the frontend already owns the speculation worker (Speculator); the pool belongs beside it
- AGENTS.md: no allocation in per-tick loops; core has no globals

## Units

- core: peo/core/executor.hpp: a non-owning parallel-for. run(pieces, body) calls body(i) once for every i in [0, pieces), in any order and on any thread, and returns when all are done. A function-reference type, not std::function (no allocation per call). A serial executor is the default everywhere; World takes one through WorldParams or a setter and passes it to its wave
- core: ScentWave's rounds pull their active tiles as pieces, each writing its own changed flag; touched() and the stale list run after, in tile order. The direction-byte refresh splits by tile with no two pieces writing one cell
- core: speculate() runs the scent update and the Dead's seconds to the boundary as two pieces of one run
- core: the Dead's decisions within one second split by unit when the batch is at least a named threshold (a tunable, default from your measurement): each unit writes its target to its own slot, then claims resolve per tile to the lowest unit index, as the serial order gives today. Below the threshold the loop stays serial
- app: a pooled executor (std::jthread workers, count = hardware threads less one for the main thread, at least 1, overridable by a command-line option) handed to the World; the speculation worker uses it. Commit stays on the main thread
- test: a shuffling executor (runs the pieces on the calling thread in a seeded random order) and a threaded one (real std::threads, test-only) both give worlds equal to the serial executor's after 200 actions on the town and a 512x512 stage with 20,000 Dead; the existing goldens pass on all three
- ci: a ThreadSanitizer preset (headless-tsan) and a CI job that runs the threaded tests under it
- docs: architecture.md's core section names the executor; the perf skill's 'core uses the executor it is given' line; research section 4 marks what is built with the measured numbers

## Acceptance

- ctest --preset headless passes (core, suite_budget, scenario_budget); the new CI job is green with zero ThreadSanitizer reports
- Serial, shuffled and threaded executors give bit-identical worlds in the new golden; every existing golden is unchanged
- headless-release with the serial executor: the saturated 512x512 update and the 512x512/50,000 Dead speculate are within 3% of today's
- headless-release with 4 workers on the M1: the saturated 1024x1024 scent update at least 2.5x faster than serial; speculate at 512x512 with 50,000 Dead faster than serial. Report 1, 2 and 4 workers for both, calm and windy (gust 2)
- No allocation per update or per speculate with any executor, warm
- Core still creates no thread: grep finds std::thread or jthread only under src/app and tests
