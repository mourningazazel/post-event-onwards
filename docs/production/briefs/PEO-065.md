# PEO-065 · Movement input: fast taps are not lost (D-032)

## Goal

Per D-032 (amends D-011). Every distinct press of a turn key is kept, up to 3 waiting, and played out no faster than 3 turns a second. A held key's auto-repeat stays capped at 3 a second, is never queued, and stops the moment the key is released. Ryan judges the feel in his next playtest, so depth and rate stay tunables.

## Context

- docs/production/decisions.md D-032; D-011 in decisions-archive/2026-09.md
- src/app/main.cpp SDL_AppEvent: kMinTurnIntervalNs, last_turn_ns, action_for, take_turn; the loop sleeps in SDL_WaitEvent (PEO-036), so a queued tap needs something to wake it
- AGENTS.md: src/app stays thin; logic in it is a bug

## Units

- core: peo/core/turn_input.hpp (+ .cpp if needed), a small TurnInput class with no SDL: `offer(Action, bool repeat, Nanos now)` and `take(Nanos now) -> optional<Action>` and `next_due() -> optional<Nanos>`. A non-repeat press is accepted at once when the cap allows, else queued if fewer than kMaxWaitingTaps (3) wait, else dropped. A repeat is accepted only when the cap allows and nothing is queued; it is never queued. Tunables in a struct (max waiting 3, min interval 1/3 s). Fixed-capacity storage, no allocation.
- app: SDL_AppEvent passes presses through TurnInput (event->key.repeat says repeat; keep using handling time, not the event timestamp, for the reason in the existing comment). When taps wait, arrange a wake at next_due() (an SDL timer that pushes a user event, or equivalent) so SDL_AppIterate or the event handler drains one per interval; idle CPU stays ~0 when nothing waits. The Action (including walk or run) is fixed at press time.
- app: N (next stage) and Escape clear waiting taps.

## Acceptance

- five taps within 0.2 s give four turns (one at once, three queued) played out at 1/3 s spacing, the fifth dropped
- holding a direction for 2 s gives about 6 turns and none after release
- a tap during a hold is kept only if the queue has room; releasing a held key never leaves repeat turns queued
- idle CPU ~0% with an empty queue (as PEO-036)

## Tests

- tests/core/test_turn_input.cpp: the acceptance timelines driven with synthetic times (taps, holds, mixed, drop at depth 3, spacing exact), plus no allocation after construction

## Manual

- peo 7: tap a direction 5 times as fast as possible, count steps (expect 4); hold a direction ~2 s then release, confirm it stops at once; alternate taps between two directions quickly and confirm order is kept. Report how it feels, for Ryan's playtest.

## Out of scope

- mouse or gamepad input
- changing the 3 turns a second cap
- key remapping
